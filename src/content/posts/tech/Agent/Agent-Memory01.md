**为什么需要Memory模块？**LLM本质是无状态推理，每次调用实际上是完全独立的，它不会自动保留过去的历史记忆。我们使用时之所以能看到它拥有记忆是因为在每次调用的时候，除了发送用户的提示词之外，还把系统提示词、用户的长期记忆、之前的对话历史上下文一并发送给了LLM。

**Memory模块的本质**，就是从过去的信息里挑出未来可能有用的部分，在合适的时刻重新提供给 Agent。

这篇文章从一个具体问题开始：Agent 如何把过去的经验留下来，又如何在未来恰好需要时找到它？我们先走一遍完整流程，再拆解写入和检索的关键设计。

## 先从整体流程看 Memory

Agent 每次调用模型时，通常只能看到当前请求和系统提供的一部分上下文。过去的会话可能很长，任务也可能已经结束，模型本身不会自动保留跨会话状态。Memory 要解决的事情，就是从过去的信息里挑出未来可能有用的部分，在合适的时刻重新提供给 Agent。

从一次交互到未来回忆，大致是这样：

```
一次对话
  │
  ├─ 写入判断：这条信息未来值得复用吗？
  ├─ 信息提炼：它是什么、适用于谁、来自哪里？
  ├─ 关系处理：它是重复、补充、更新还是冲突？
  └─ 持久保存：放入合适的记忆范围
          │
          ▼
未来的新任务
  │
  ├─ 理解当前问题和任务目标
  ├─ 限定搜索范围
  ├─ 找出相关候选记忆
  ├─ 排除过期、被取代或不够相关的条目
  └─ 将少量、带来源的记忆提供给 Agent
          │
          ▼
Agent 结合当前要求、项目事实和记忆作答或行动
```

因此，Memory 至少有两大工作面：**写入**和**检索**。

写入不是“把聊天存进数据库”，而是把对话转换成适合未来复用、能够解释来源和变化的记忆单元。检索也不是“把数据库内容全部塞给模型”，而是从大量候选中，找出对当前任务有帮助的少量信息。

两者可以分别封装成 Agent 工具，例如 `memory_write` 和 `memory_search`。工具负责让模型表达意图，记忆服务负责存储、过滤、排序和约束更新。但它们不一定只能通过模型工具调用：Harness 也可以在模型请求前自动做一次轻量检索，避免 Agent 忘记调用搜索工具。一个可讨论的组合是：

- 写入由 Agent 主动调用工具，明确表达“这条值得记住”。
- 每次请求前由 Harness 做一次低成本、严格限范围的自动召回。
- 当 Agent 发现还缺少过去的细节时，再调用搜索工具做深入检索。

在讨论具体设计前，需要先把 Memory 与几种相近的数据分开：

| 信息类型 | 回答的问题 | 例子 |
|---|---|---|
| 指令 | Agent 必须或应该怎么做？ | `AGENTS.md` 中的项目规则 |
| 当前任务状态 | 这项任务目前做到哪里？ | 目标、进度、已确认决定 |
| 会话历史 | 当时具体说过或执行过什么？ | 用户原话、工具调用和结果 |
| 长期记忆 | 哪些过去经验可能帮助未来任务？ | 稳定偏好、项目背景、已确认决策 |
| 项目文件与产物 | 当前权威事实是什么？ | 源代码、配置、设计文档 |

记忆是未来推理的参考，不是规则文件，不是任务状态数据库，也不是原始对话的替代品。

## 写入：从对话变成可管理的记忆

### 第一步：判断值不值得记

Agent 可能从对话中发现很多信息，但并非每条信息都适合留下。写入判断应优先回答：

1. 未来是否可能再次用到？
2. 是否稳定到足以跨会话复用？
3. 是否来自用户明确表达或可靠证据，而不是模型猜测？
4. 是否可以从当前项目文件直接重新获得？
5. 是否包含密码、API Key 等敏感信息？
6. 它属于长期记忆，还是仅属于当前任务或会话？

适合长期保留的常见内容包括稳定的用户偏好、反复出现的纠正、项目中难以从代码推导的背景，以及影响后续工作的已确认决定。普通闲聊、一次性任务要求、未经确认的猜测和大段原始材料通常不应直接变成长期记忆。

这里需要区分“用户要求执行”和“用户要求记住”。“这次回答详细一些”首先是当前任务要求；“以后默认回答详细一些”才明确表达了长期偏好。Agent 应能识别这种差异。

### 第二步：决定记忆单元和类别

一个好的记忆单元应该短、单一、可以独立检索和更新。不要把一整段聊天压成含有多个主题的模糊摘要。

例如，下面这条包含两个独立信息：

> 用户喜欢简洁回答，并且 MiniCC 项目使用 Python 3.12。

更容易管理的做法是拆成：

- 用户偏好：跨项目回答默认简洁。
- 项目事实：MiniCC 当前使用 Python 3.12。

类别的意义不是为了让表格看起来整齐，而是决定记忆应该如何被理解、检索和更新。一个起步足够的分类可以是：

| 类别 | 主要内容 | 典型更新方式 |
|---|---|---|
| 用户偏好 | 表达方式、协作习惯、工具偏好 | 用户明确改变偏好时更新 |
| 用户纠正 | 对 Agent 行为的明确纠正 | 相同错误再次出现时强化；过时后可撤销 |
| 项目事实 | 项目背景、架构、技术约定 | 当前文件或新事实核实后更新 |
| 决策 | 用户已确认的方案、接口、范围 | 保留决策历史，记录被哪个决定取代 |
| 经验或过程 | 未来任务可复用的做法和教训 | 根据后续使用效果整理或淘汰 |

类别不宜过细。分类过多会让模型难以稳定选择，也让搜索依赖脆弱的标签。类别应该对应不同的生命周期和检索方式，而不是给每个话题单独造一个类型。

还要区分“记忆类型”和“记忆范围”：类别说明内容是什么；范围说明它在哪些任务或项目中适用。

### 第三步：确定记忆范围

常见范围至少有：

- **全局范围**：适用于该用户的大多数项目，例如稳定的沟通偏好。
- **项目范围**：只适用于一个仓库、产品或团队，例如项目架构和项目决策。
- **会话或任务范围**：只在当前任务有效，不应自动升级成长记忆。

范围是隔离边界，不只是一个描述字段。检索项目任务时，应先限定当前项目及全局记忆；不应把另一个项目的约定因为关键词相似就召回。

Agent 可以提出范围，但程序还应根据当前工作区和记忆策略约束允许的范围。如果无法确定一条信息是否跨项目适用，就不应轻易写进全局记忆。对于编码 Agent，项目相关事实默认项目级通常比默认全局安全。

### 第四步：关联来源、时间和可信度

记忆正文之外，还需要保留解释它的元数据：

- 唯一 ID；
- 类别和适用范围；
- 创建与更新时间；
- 来源会话、消息或用户确认；
- 来源类型，例如用户明确指示、用户纠正、Agent 提取或代码证据；
- 有效状态，必要时记录生效和失效时间；
- 与相关或被取代记忆之间的关系。

“用户明确说过”和“Agent 根据上下文推测”不能拥有相同的证据等级。来源不是装饰信息：它决定冲突时该相信谁，也让用户能检查 Agent 为什么会这么记。

### 第五步：处理新记忆与旧记忆的关系

写入不是简单的 `append`。新信息可能和旧记忆有多种关系：

| 关系 | 例子 | 建议处理 |
|---|---|---|
| 完全重复 | 同一偏好重复表达 | 不新增，或只补充证据 |
| 语义重复 | “默认简洁”与“少讲背景”表达相同偏好 | 合并为同一条的新增来源，不重复堆积 |
| 补充 | 新增一条偏好的适用条件 | 保留旧内容，关联并补充条件 |
| 时间变化 | “目前住在杭州”，之前住在上海 | 新记录标为当前有效，旧记录保留历史时间 |
| 明确更正 | 用户说“我之前说错了，以后改用 uv” | 新记录生效，旧记录标记为被取代，并保留来源 |
| 矛盾但范围不同 | 工作项目偏好简洁，教学项目偏好详细 | 两条都保留，按范围检索 |
| 无法确定 | 用户说“今天先详细讲”，不清楚是否长期改变偏好 | 仅按当前任务执行；必要时简短确认是否更新长期偏好 |

这里有个重要原则：**新记录不应仅凭“时间更晚”就自动覆盖旧记录。**

“我搬到了杭州”是事实变化；“我这次想要详细版”不一定是偏好变化；“我更正一下，以后请用简洁模式”则明确改变长期偏好。系统需要判断它们属于哪种情况。

模型可以负责提出关系判断，但程序应限制哪些状态变化允许发生。比如只有具有足够证据的明确更正，才能把旧记录标成被取代；无法判断时先保留冲突，不让某个模型的一次猜测直接删除历史。

一种稳妥的数据模型是保留记录和关系，而非覆盖原文：

```
记忆 A：用户偏好简洁回答
  状态：被取代
  来源：2026-08 的明确表达

记忆 B：用户偏好详细回答
  状态：当前有效
  来源：2026-11 的明确更正
  取代：记忆 A
```

这样既能回答“现在应该遵循什么”，也能解释“之前为什么采用另一种做法”。

### Codex 和 Claude Code 的启发

Claude Code 将用户编写的指令文件与自动记忆分开。指令文件负责项目规则；Auto Memory 则记录 Claude 从纠正、偏好和不容易从代码推断的项目背景中学到的内容，并按仓库组织。官方文档还说明，自动记忆会以有限内容加载；指令和记忆都是模型上下文，不是强制权限控制。[Claude Code：How Claude remembers your project](https://code.claude.com/docs/en/memory)

Codex 的本地记忆默认关闭。用户开启后，它会在后台从符合条件的过往对话生成记忆文件，跳过仍活跃或很短的会话，并过滤生成内容中的秘密信息。用户可以按对话分别控制“是否读取已有记忆”和“是否贡献未来记忆”。[Codex：Memories](https://learn.chatgpt.com/docs/customization/memories?surface=app)

两者共同说明：自动提炼应该降低用户维护成本，但系统仍要区分记忆与正式指令，并给用户提供关闭、检查和删除的控制权。Codex 的后台整理也提醒我们：写入时间和对话结束时间可以分开，不必为了每条候选记忆都阻塞当前任务。

## 检索：从记忆库找到当前真正需要的内容

假设 Agent 已经积累了几百条记忆。用户问“这个项目怎么启动”，要找到正确的项目运行命令；用户问“我平时喜欢怎么安排学习计划”，要找到个人偏好。单纯让模型读取所有记忆既昂贵，也容易把无关内容混进推理。

检索至少要完成以下步骤：

```
当前用户问题 + 当前任务状态
            │
            ▼
构造检索意图和查询词
            │
            ▼
范围过滤：当前用户、当前项目、允许的记忆类别
            │
            ▼
候选召回：关键词、语义、实体、时间
            │
            ▼
      候选合并与排序
            │
            ▼
相关度门槛 + 有效状态过滤
            │
            ▼
Token 预算内选取少量记忆
            │
            ▼
带来源、时间和状态注入上下文
```

### 第一步：理解这次要找什么

检索查询不应永远只是当前最新一句话。用户可能在前几轮明确了任务目标，当前这一句只说“那继续吧”。此时检索应结合当前消息、任务目标和必要的近期对话来构造查询。

另一方面，如果用户问的是“上周我们最后决定了什么”，这更像是搜索会话历史；如果用户问“通常的代码风格是什么”，才更像检索长期偏好或项目规则。记忆检索不能替代对话历史搜索。

### 第二步：先过滤范围，再计算相关度

范围过滤应在语义排序之前进行。先限定当前用户与当前项目，再判断哪些记忆相关。这样既提高效率，也减少数据串用。

项目文件、正式指令和记忆之间也有不同的权威级别。记忆只提供提示。若项目里的当前配置与旧记忆不一致，应以当前文件核实；若用户当前要求与一般偏好不同，应遵循当前要求。

### 第三步：混合召回，不依赖单一搜索方式

不同检索方法擅长的问题不一样：

- **关键词检索**适合准确名称、命令、路径、ID 和术语。
- **语义检索**适合词面不同但含义相近的表达。
- **实体检索**适合围绕人、项目、组织或工具查找相关记忆。
- **时间过滤与排序**适合“现在”“上次”“最近变化”等时间问题。

成熟系统通常组合多个信号，而不是认为向量搜索能解决所有检索问题。Mem0 文档描述了语义、BM25 关键词、实体匹配、过滤阈值和可选重排；它也建议用用户/Agent 等标识限定搜索范围。[Mem0：How it works](https://github.com/mem0ai/mem0/blob/main/docs/core-concepts/how-it-works.mdx) [Mem0：Search Memory](https://github.com/mem0ai/mem0/blob/main/docs/core-concepts/memory-operations/search.mdx)

LangGraph 的做法更像提供底层构件：应用可以使用命名空间隔离的 Store 和语义搜索，但由应用决定何时搜、搜哪些范围、以及分数不够时是否注入。[LangGraph：Memory](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/add-memory.mdx)

对一般个人和项目记忆，通常先做好范围过滤、关键词与语义混合召回、相关度门槛和结果解释，就比直接引入完整知识图谱更重要。

### 第四步：融合候选、重排并拒绝低相关结果

关键词和语义检索可能找到不同候选，系统需要把它们合并。候选可以按多种信号综合排序，例如：

- 与当前问题的语义相似度；
- 关键实体是否匹配；
- 是否属于当前项目；
- 记忆当前是否有效；
- 是否有用户明确确认的来源；
- 时间是否符合问题中的时间意图。

然后设定相关度门槛和结果数量上限。低于门槛的记忆不应为了“让模型有东西可看”而硬塞进上下文。必要时可以让轻量重排器重新判断少量候选，但需要衡量它增加的延迟和调用成本。

时间新旧不能被当成普遍的质量分数。对于“当前工具版本”，新信息可能更可靠；对于“过去做过什么决定”，旧信息仍然是准确的历史记录。

### 第五步：控制注入并提供来源

检索结果应是短小、可读、带元数据的记录，而不是一大段无来源的摘要。例如：

```
[项目事实 | 当前有效 | 用户确认 | 2026-11]
MiniCC 的博客文章保存在 erode-blog 的 tech/Agent 目录。
来源：会话 8d31，轮次 14
```

这样 Agent 能区分这是当前有效的项目事实、它的来源是什么，以及它是否只是一个旧的假设。上下文里还应提醒模型：记忆是未必完整的历史参考，不是高优先级指令。

Letta 的架构提供了另一个有用区分：小而频繁使用的信息可以放在持续可见的核心记忆中；更大、低频的信息则放在上下文窗口之外，通过搜索工具按需取回。[Letta：Memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks) [Letta：Archival memory](https://docs.letta.com/v1-sdk/memory/archival-memory)

## 冲突处理：先保留证据，再决定当前状态

记忆冲突是写入和检索共同面对的问题。写入时要判断新旧记录是什么关系；检索时要避免把已过期或已被取代的记录当成当前事实。

建议将“冲突解决”拆成两层：

1. **事实层保留历史**：原始记录、来源和时间不被悄悄抹掉。
2. **当前视图确定状态**：系统明确哪些记录当前有效、哪些已被取代、哪些互相矛盾而尚未解决。

对用户偏好，明确的长期纠正可以取代旧偏好；对项目事实，应尽量核对当前仓库文件；对决策，应保留每次确认和取代关系；对时间变化，应记录有效时间，而不是把历史说法判成错误。

Graphiti 使用带有效时间的事实关系，并保留原始事件来源，支持查询“现在是什么”以及“过去某个时间是什么”。这适合关系复杂、事实经常变化的领域，但需要图数据库、实体抽取和事实维护流程，复杂度显著高于普通记忆库。[Graphiti README](https://github.com/getzep/graphiti/blob/main/README.md)

这也说明，冲突处理不能只交给一个模型做最终裁决。模型可以提出“可能是更新”或“可能矛盾”，但系统还需要检查它们是否同一对象、同一范围、同一时间条件，再按来源权威和用户确认程度决定状态变化。

## 用户如何管理记忆

自动化不应让记忆变成一个用户看不见的黑盒。用户至少应该能：

- 查看全局和项目记忆；
- 搜索某条记忆；
- 查看来源和变更历史；
- 编辑错误内容；
- 删除不想保留的内容；
- 对是否自动读取、是否贡献记忆进行控制。

“查看召回解释”也很重要。用户不仅要知道系统存了什么，还应能回答“为什么本次对话会把这条记忆带进来”。否则检索错误很难被定位和修正。

## 怎样评估 Memory 是否真的有效

记忆写入成功，不代表记忆系统有效。评估应覆盖整个闭环：

| 维度 | 要回答的问题 |
|---|---|
| 写入精度 | 保存的内容有多少是真正值得复用的？ |
| 写入召回率 | 重要的用户纠正和决定有没有漏掉？ |
| 检索精度 | 检索出来的记忆是否与当前任务相关？ |
| 检索覆盖率 | 问到旧决定时，系统能否找回正确记录？ |
| 冲突准确性 | 系统能否区分重复、补充、时间变化和真正矛盾？ |
| 过期控制 | 被取代的旧事实会不会继续影响当前回答？ |
| 安全性 | 敏感值、外部恶意指令会不会进入并影响记忆？ |
| 用户控制 | 用户能否理解、纠正和删除系统的记忆？ |

测试数据应来自真实任务，并包含跨项目、长时间间隔、相似但不相关的记忆、偏好变化和历史决策回溯。只用“存入后能否查出来”做测试，覆盖不到记忆真正的风险。

## 一个务实的实现顺序

Memory 很容易因为向量、知识图谱、时间数据库和多模型协调而变得过度设计。更稳妥的顺序是：

1. 明确记忆记录结构、类别和范围规则。
2. 建立来源、时间、状态和版本关系。
3. 先实现同范围候选检索、重复识别和保守冲突策略。
4. 用真实对话建立写入、召回和冲突评估集。
5. 如果关键词召回确实遗漏，再加入语义检索；如果排序仍不可靠，再评估重排。
6. 只有当实体关系和时间查询成为真实需求时，再考虑知识图谱。

成熟 Memory 系统的关键，不是一次性选中最复杂的存储技术，而是让写入、检索、更新和用户纠正形成可观察、可验证的闭环。

## 总结

Agent Memory 可以用两个核心问题来理解：

- **写入**：这段经历中什么值得未来复用？它是什么类型、适用于什么范围、来自什么证据？遇到新旧信息时，是重复、补充、变化还是冲突？
- **检索**：当前任务真正需要什么过去信息？如何先限制范围、再结合多种信号找到相关候选，过滤过期信息，并在预算内把证据交给 Agent？

写入决定“系统记下了什么”，检索决定“系统在什么时候想起什么”。冲突和时间变化则决定它是否能从过去走到现在而不把旧判断误当成新事实。

所以，Agent 的记忆不是一个存储功能，而是一套**对经验进行筛选、组织、召回、更新和纠错的上下文管理系统**。它最终应减少重复解释和重复犯错，同时让每条影响 Agent 判断的记忆都能被追溯、质疑和修正。
